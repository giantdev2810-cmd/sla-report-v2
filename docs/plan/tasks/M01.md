### Proposed calculation and data policies

| Area | Proposed choice and cost/limit |
| --- | --- |
| Rules | Reuse T05; implement the other six rules as pure Python functions and assemble exact contract rows/summary. Sort output rows and responder groups by ID for deterministic review. No new dependency. |
| Equal event timestamps | Use (at, id) ascending as the deterministic order: lowest ID for earliest, highest ID for latest. Record this interpretation in DECISIONS; the brief does not define the tie-break. |
| Calendar | Use zoneinfo and site-local dates/hours/holidays; intersect work windows with elapsed UTC instants, sum seconds, then floor once. Overnight windows carry into the next day and holidays exclude that local day's portion; union overlapping work intervals. |
| Ambiguous calendar input | Reject ambiguous/nonexistent local deadline or work-boundary times rather than silently choose a DST offset. Missing required site/calendar/current-responder data or invalid required values makes the load fail, not omit rows or substitute historical actor names. This can prevent a report on unsupported/invalid upstream data. |
| References and acquisition | Load sites, all site holidays and staff. Scan unfiltered requests with per_page=100, following the largest reported total_pages, not ceil(total/per_page). Local site-date filtering selects requests needing full events. Avoid relying on unverified upstream date-filter timezone. More request pages are downloaded. |
| Reconciliation | Compare two full request walks for the selected range's IDs/payloads, acquire complete event pages for included requests, then make a third request walk to check that selected request state still agrees. Any observed disagreement fails the load with no partial publication. Agreement is a practical check, not proof that a faulty upstream API omitted nothing. |
| Duplicate versions | Deduplicate requests by ID, keeping the greatest valid updated_at within a walk. Equal updated_at with different payloads fails. Deduplicate events by ID and reject conflicting copies; unresolved event references after full traversal fail. No silent arbitrary overwrite. |
| Store | One worker, one serialized on-demand load. Build separate data then publish the snapshot atomically; give report calculations a private copy. Cache the last successful range for subrange queries, without automatic live refresh in M01. Other ranges require a new load. Costs include copies and possibly long first-report latency. |
| Feed | No change-feed request in M01; baseline comes from requests/events. Live refresh/recovery belongs to M03. Baseline reconciliation does not claim a transactionally consistent upstream snapshot. |
| HTTP | Reuse a synchronous httpx client per load, with sequential GETs and at least 250 ms between request starts. Timeout at most ten seconds or the remaining deadline. At most three attempts per GET: retry transport errors and 500/502/503/504 after 1/2 seconds; 429 waits at least valid Retry-After. A missing/invalid Retry-After or wait beyond the deadline stops the load. All attempts count against limits. |
| Limits | Each load is bounded to 6000 upstream GET attempts and thirty minutes; no recursive/unbounded retries. Budget/page/no-progress failure aborts instead of publishing partial data. These are MVP safety limits, not the level 2 performance targets. |
| HTTP contract | Strict YYYY-MM-DD from/to, required once each, inclusive, reversed dates invalid: 400. Upstream malformed/conflicting data: 502; transport/rate/budget/unusable-load failure: 503. Return safe error codes/messages without credentials or payloads. Keep health and browsing starter behavior; ready stays 503 until six-month usability is verified, not merely because one report succeeded. |
| Page | Render request rows and responder summary; show loading/error/empty states and disable duplicate submission during a load. Use textContent for upstream names. Keep implementation details out of normal product flow. |

The first load may take minutes; M02 optimizes six-month startup/report timings.
Failing on detected inconsistency favors visible failure over a misleading result,
but can prevent an MVP report while the upstream changes. Repeated walks still
cannot prove complete acquisition or a single upstream transaction snapshot.
